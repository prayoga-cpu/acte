## D-009 · `apps/api` runtime is tsx everywhere, not a compiled artifact — DECIDED
**Date:** 2026-09-22 · **Owner:** Darwin
**Decision:** `pnpm --filter @acte/api start` runs `node --import tsx src/main.ts`, the same way `dev` does (minus `--watch`). There is no `node dist/main.js` production path.
**Why:** `packages/contracts` ships TypeScript source with extensionless internal imports (works under tsx, vitest, and Next's webpack via `moduleResolution: "Bundler"`). Plain Node's ESM loader needs explicit `.js` extensions and doesn't reliably fall back to sibling `.ts` files across the experimental type-stripping and non-type-stripping code paths — chasing that compatibility (tried: adding `.js` extensions everywhere) broke the web app's webpack build instead. tsx sidesteps the whole class of problem by using bundler-style resolution consistently in every environment.
**Consequence:** Before a real Scaleway deployment, revisit this — either accept tsx in production (used in production by real projects; images just need Node not just static JS) or invest in bundling `apps/api` with esbuild/tsup so `packages/contracts` gets inlined and Node's strict resolution stops mattering. `tsc -p tsconfig.build.json` (`pnpm build`) is kept as a type-check-shaped CI sanity step even though its `dist/` output isn't used to run anything.

## D-013 · Hosting on Vercel instead of Scaleway — DECIDED for beta/testing, OPEN for production
**Owner:** Darwin (recommendation), Yann (sign-off on the production half, since it changes what Annex A and the client's own account arrangement cover) · **Blocks:** any production deploy or demo to a real firm
**Context:** `CLAUDE.md` §5 names Scaleway (Paris region, client-owned account) as the hosting stack, and the Privacy Policy already published at `/privacy` (grounded in `docs/03-security/PRIVACY_MODEL.md` rule 6) commits to a closed sub-processor list — Scaleway, Brevo, Stripe, Sentry EU — that does not include Vercel. Darwin started configuring a Vercel "New Project" import of `apps/api` (NestJS preset) on a personal Hobby team (`prayoga-development`), explicitly considering Vercel as the real hosting plan rather than a personal preview.
**Technical friction specific to `apps/api` on Vercel, found while reviewing the import screen:**
- D-009 (DECIDED) runs the API via `tsx` everywhere with no compiled `dist/main.js` — Vercel's NestJS preset assumes a build producing one. Running it via `tsx` on Vercel instead is nonstandard and untested here.
- The API holds a persistent Postgres connection pool (Drizzle) and cookie-session auth (better-auth), both built assuming a long-running process. Vercel Serverless Functions are stateless/per-invocation; without a pooler (PgBouncer or an HTTP-based Postgres driver) this risks exhausting DB connections under concurrency.
- Region/account control: a Hobby team is not a client-owned account, and Vercel region pinning is limited on that tier — both cut against the France-hosting commitment already in the published Privacy Policy.
**Options:**
1. Keep Scaleway for `apps/api` as originally planned; optionally put `apps/web` (Next.js, a first-class Vercel fit with none of the above friction) on Vercel instead, as a split-hosting arrangement.
2. Move both apps to Vercel, accepting: re-architecting `apps/api`'s DB access for serverless, revisiting D-009, moving off a Hobby/personal team to a client-owned one, and rewriting the Privacy Policy's sub-processor list and hosting claims (client notice required per the privacy rule above) before any real firm sees it.
3. Some other host entirely (Railway, Render, Fly, a Scaleway Instance/Container) for `apps/api`, keeping the Vercel option only for `apps/web`.
**Decision:** Darwin chose to deploy **both** `apps/web` and `apps/api` to Vercel (personal Hobby team `prayoga-development`) now, explicitly scoped to **beta/testing only** — synthetic data, informal testers, not a client demo or production traffic. Whether real production hosting must be Scaleway (or something else) stays OPEN and is tracked as a Stage 1 TODO in `STATUS.md` — do not treat this beta deploy as satisfying that question, and do not point a real firm at these URLs. Because `apps/api/src/main.ts` bootstraps a traditional `app.listen(port)` server (D-009's actual local/Scaleway-bound entry point), which doesn't map onto Vercel's request-handler serverless model, added a **separate, additive** Vercel-only entry point: `apps/api/api/index.ts` (wraps the same Nest `AppModule`, exposes its Express instance as a request handler, bootstraps once per warm container) plus `apps/api/vercel.json` (rewrites every path to it). `src/main.ts` and the `dev`/`start` scripts are untouched — this only adds a parallel path for Vercel, it doesn't change how the app runs anywhere else.
**Consequences:**
1. Serverless cold-starts will re-run `NestFactory.create()` (and open a fresh Postgres connection) more often than a long-running Scaleway process would — acceptable at beta-test traffic levels, not something to scale up on as-is.
2. `apps/api` needs a real, network-reachable Postgres instance (Vercel doesn't provide one on the Hobby plan by default — use its Neon/Supabase marketplace integration, or any other managed Postgres) since there's nowhere to run `docker-compose`/a native install on Vercel.
3. `WEB_ORIGIN` (API env) and `API_ORIGIN` (web env) must point at each app's real deployed Vercel URL, or auth (CORS + the better-auth cookie flow) breaks.

## D-014 · Admin console and notifications built on interim defaults for D-004 / D-005 — DECIDED (interim, pending Yann)
**Date:** 2026-09-23 (revised 2026-09-24 after an adversarial pre-push review) · **Owner:** Darwin (interim call) · Yann (the real decision, still owed)
**Context:** Every remaining unbuilt Stage 2 feature (Admin console, invite flow, Subscription tab UI, Notifications) depends on D-004 or D-005, both OPEN and owned by Yann. Darwin was asked directly whether to wait or build on a stated default, and chose to build using this file's own recommendations — same override pattern as D-011.
**Decision:**
- **D-004 → role-gated, server-enforced** (D-004's own written recommendation). `AdminGuard` (`apps/api/src/auth/admin.guard.ts`) runs after `SessionGuard` on every `/v1/firm/*` route and returns 403 to non-admins. In the web app the console is reached from the profile menu ("Console Admin (Cabinet)"), exactly where the prototype puts it, rendered only for admins — the server remains the boundary.
- **D-005 → in-app only** (no external channel, no new sub-processor). `notification` table + header bell. Rules: dossier budget ≥ 80 % (lawyer + admin), a member's oldest pending task > 48 h (admin), an invitation unanswered 48 h after its last send (admin). Each alert is an *episode*: it stays read while its condition holds, closes when the condition clears, and a partial unique index keeps one open episode per (member, type, ref). Low-confidence is stage 5.
**How invitations work (revised — the first version was unsafe, see below):**
- A pending invite is an `invitation` row (firm, email, role, sha256 of the token, expiry), **not** a `member` row. Pending uniqueness is per (firm, email), so one firm's invitation can't reserve or block an address for another firm, and duplicate checks never reveal whether an address has an account elsewhere.
- **Joining a firm is token-bound.** The only path is `POST /v1/invitations/:token/accept {name, password}`: it creates the account for the *invitation's* email (the client can't supply one), then binds it to that invitation's firm in one transaction that re-checks the token hash, "still pending" and expiry. The account is marked email-verified (the emailed token proves the inbox). A plain signup — password or magic link — **never** joins an existing firm; it always founds a new one.
- Suspension revokes access everywhere: no session is issued to a suspended member (`session.create.before` → 403 `MEMBER_SUSPENDED`), their existing sessions are deleted, and `SessionGuard` rejects them.
- The Subscription tab is a UI simulation — Stripe is stage 6 — carrying the prototype's own "simulée" disclaimer.
**What the first version got wrong (2026-09-23, never pushed):** it stored invites as `member` rows and joined a new signup to a firm by matching its **email**, with the token only gating a preview page. Anyone who signed up first with an invited address joined that firm and could read its dossier names; any self-registered admin could "invite" a stranger's address to capture that person's later signup; and this file claimed that was "no weaker than founder signup" — which was wrong. Caught by a 5-lens adversarial review before push, redesigned as above, and covered by e2e tests (`apps/web/e2e/admin-console.spec.ts`).
**Known limitation — blocks onboarding a real firm:** there is still **no email verification** on plain signup. Someone who registers an address before its owner does (1) blocks that person's invitation (`409 account_exists` — an account belongs to one firm, and there's no self-serve move), and (2) keeps a password on an account the real owner may later reach by magic link. Neither exposes another firm's data any more, but both need `requireEmailVerification` + a Brevo verification email (and the seed marking demo users verified) before a real firm onboards.
**If Yann decides differently:** ungated → drop `AdminGuard` from `AdminController`; email digest → add a sender beside the in-app episodes in `NotificationsService`.

## D-015 · LLM chat in "Le Cerveau d'ACTE" via Mistral — DECIDED for local/beta testing, OPEN for production
**Date:** 2026-09-28 · **Owner:** Darwin (override, testing) · Yann (production sign-off and client notice)
**Context:** `ROADMAP.md` stage 2 says the Cerveau panel uses "deterministic templated insights (no LLM yet)", and `CLAUDE.md` §5/§8 lists no LLM provider (stop and ask before adding a third-party service). `PRIVACY_MODEL.md` rule 6 already anticipates "Mistral (EU, stage 5+, only per D-002)", but the published `/privacy` page lists only Scaleway, Brevo, Stripe and Sentry, and promises a documented decision **and prior notice to client firms** before any new sub-processor. After an analysis recommending against building it yet (stage 5, not covered by the agreement, B2), Darwin supplied a Mistral API key and explicitly asked to implement it so it can be tried in the app UI — same override pattern as D-011.
**Decision:** Built the panel's free-text chat on an LLM, **off by default**. Everything else in the panel (the "Analyse IA" insights, Insights Cabinet, activity feed) stays deterministic.
- `POST /v1/me/chat` (`apps/api/src/brain/chat.*`), contracts in `packages/contracts/src/llm.ts`. Enabled only when `LLM_CHAT_ENABLED=true` **and** `LLM_API_KEY` is set; otherwise it answers 503 `llm_disabled` and the web app keeps the existing deterministic `botReply` (also its fallback on any error or rate limit).
- **What reaches the provider** — two different things. (1) An `LlmChatContext`: numbers, booleans, enums and opaque refs `D1`… only (`.strict()` at every level, at most 40 dossiers, parsed at runtime, so no field can carry a name), covering the caller's own summary and the firm's **active** dossiers (most-consumed budget first; archived ones left out) — nothing about other members (rule 4). This part is P3 by construction. (2) The member's own chat turns: **free text**, pseudonymized best-effort before sending (`apps/api/src/brain/pseudonymizer.ts`):
  - every dossier name and client label (full phrase) → the dossier's ref `[Dn]` (`[dossier]` when two dossiers share it) — except a name that is a single stop word ("Petit"), or only a link, e-mail, phone or file (the masks cover those);
  - every word of those (taken from the raw name, so "Cdiscount" counts in "Cdiscount.com" and "Kerbrat" in an e-mail label) that is not in a stop list of common, legal, web and chat words → the ref when it looks like a proper name (any capital, a caseless script, a digit, or a name with no proper casing at all), otherwise `[dossier]` — masked but not attributed; a single character counts in scripts where it can be a name (王); tokens joined by punctuation are also registered split and joined (N'Diaye / Ndiaye, H&M / HM, S.N.C.F. / SNCF); and reference numbers (two or more adjacent number groups such as `21/04567`, or one group of 5+ digits);
  - the member's last 500 task titles typed word for word → `[tâche]` (punctuation and spacing between words don't matter, except inside or right next to a link, e-mail, phone number or filename; titles made only of common words, or only of a link, phone or file, are skipped);
  - links (`http(s)`, `(s)ftp`, `smb`, `file` URLs, `www.`, or a bare domain ending in a common TLD, with an optional port), e-mail addresses (local part up to 128 characters, including one glued to another), any whitespace-free token of up to 1,024 characters ending in a common office or media extension (brackets and paths included: `S:\Clients\…\Conclusions(1).docx`), phone numbers (French `0X XX XX XX XX` and international `+CC`, `00CC`, `(+CC)`, optional `(0)`), and 6+ digit runs → a mask;
  - words are compared folded, on both sides: diacritics (NFKD plus a table of stroke, hook, bar and ligature letters such as ł, ŀ, ħ, ɗ, ƚ, ө, қ, æ, œ, ß), case and invisible characters (soft hyphens, zero-width characters, the tatweel) are ignored; punctuation, apostrophe-like letters (ʼ, ʻ), superscript/subscript/circled digits (², ₂, ①), spacing, emoji and symbols separate words. Invisible and private-use characters are removed before the masks run, and text is sent in NFC.
  **Restored names never go back.** Each reply comes back twice: `reply`, with names restored, for the member; and `history`, the same reply with refs, which the panel sends back as the assistant turn (fallback replies are not sent at all). The API still pseudonymizes every history turn, keeping the refs in the model's own. A `[Dn]` the member types loses its brackets, and only refs the model was shown — in the figures or the conversation, not the prompt's example — are restored (bracketed form only: a bare `D12` is a cote or a road). History turns are cut to 1000 characters, on a code-point boundary, only after pseudonymizing. Lookup is by hashed word sequences (multipliers drawn per process, so colliding names can't be precomputed), never a regex built from a name; every mask is anchored and bounded; matching is linear. Measured on a laptop: ~150 ms to build for 3,000 dossiers at maximum field sizes plus 500 titles, ~3 ms to redact a maximum-size request; worst cases found ~0.55 s to build (names cycling through every Unicode letter, cold cache, just under the budget) and ~75 ms to redact (nested adversarial names). The chat **fails closed** (503 `llm_unavailable`, no provider call) past 1,200,000 characters of names, labels and titles or 300,000 registered words, rather than mask some names only. This part is **not** P3-limited: see the residual risk below.
- Provider-agnostic: an OpenAI-compatible client over `fetch` (no SDK dependency). Defaults to Mistral's API (`https://api.mistral.ai/v1`, `mistral-small-latest`). Moving to Scaleway Generative APIs (Paris, already the planned host) needs three settings and no code change: `LLM_BASE_URL=https://api.scaleway.ai/v1`, a Scaleway secret key in `LLM_API_KEY`, and a Scaleway model id in `LLM_MODEL` — e.g. `mistral-small-3.2-24b-instruct-2506` from Scaleway's supported-models list as of 2026-09-28; Mistral's `-latest` aliases don't exist there.
- No prompt, reply or provider error body is logged — only the HTTP status. Rate limits are in memory and **per instance**: 20 questions per member and 300 in total per 10 minutes, one request in flight per member and 8 per instance; each Vercel serverless instance counts separately, so a shared store (Postgres) is needed before production. Replies are rendered as React text and stripped of Markdown; a reply that is empty after stripping answers 503 `llm_unavailable`.
- Tests: `chat.service.test.ts` types every canary — a dossier name, a client label, an archived dossier with non-Latin-1 diacritics, two task titles (one containing a filename), a filename, an e-mail, a link, two phone formats and a 6+ digit run — into the message **and** into both history roles (the assistant turn carrying restored names and emoji), and asserts none reaches the provider, any `console` method, or `process.stdout`/`stderr` (NestJS's Logger writes there); it also checks the ref-form `history`, that truncation happens after pseudonymizing, the shown-refs rule, one request in flight per member, and failing closed. `pseudonymizer.test.ts` carries a reproduction of every pseudonymizer finding from the three review rounds, plus time budgets for adversarial inputs. `packages/contracts/src/llm.test.ts` asserts the context allowlist rejects a name. The web behaviour (reply filling the typing bubble in place, dictation sending the live input, history sent in ref form) was checked in a headless Chromium harness with a mocked API, not by a committed test.
- **Adversarial review (2026-09-28), three rounds.** Round 1 (5 lenses, 3 skeptics per finding, majority keeps; 63 agents) confirmed 16 of 19 findings, the worst being accents outside a fixed French table (Dvořák, Şahin reached the provider, even with no typing, via restored names echoed back in history) and one regex per name with `\s+` per space (catastrophic backtracking: any self-signed-up account could freeze the API). Round 2 (each finding re-run against the fix plus 3 fresh lenses; 79 agents) found that fix incomplete — 20 more confirmed, including an emoji offset bug that leaked names and a per-character trie that could take seconds and exhaust memory — and led to the word-level design. Round 3 (32 rechecks plus 3 fresh lenses; 107 agents) finished after the first push (`fd49b78`): 22 more confirmed, among them names made only of stop words never masked, crafted hash collisions (~4.4 s per request), words inside a link or e-mail in a name never registered, H&M / S.N.C.F. never masked, and still more ways for a restored name to leak on the way back — which is why history now travels in ref form. All fixed in the follow-up commit.
**Residual risk — why production stays OPEN:** the chat box is free text, and the pseudonymizer only knows what ACTE stores. Sent as typed: names ACTE doesn't know (an opposing party, a judge, a colleague — "Me Rivoal" outside the full task title); part of a task title, a title older than the member's last 500, a title typed with different words, or one whose link, e-mail, phone number or filename is spaced or punctuated differently from the stored title; a known name typed with a space or an apostrophe added that the stored name lacks (Ndiaye stored, "N'Diaye" typed; Lafontaine / "La Fontaine"), spelled differently (Mueller / Müller), glued to other letters or digits ("Kerbrat2"), or — in scripts written without spaces (Chinese, Japanese, Thai) or with attached particles (Korean, Arabic prefixes) — inside a longer word; a filename containing spaces (only its last word is masked), with an uncommon extension, or over 1,024 characters; phone numbers in other formats; links with no scheme, no `www.` and no common TLD; pasted document or e-mail content (P0/P1); and a one-word name that is a stop word ("Petit"; Lê → "le") typed alone. Two usability limits, not leaks: an ordinary word in a dossier name or task title that is not in the stop list — or a name made only of stop words, such as "Grand Est" in "le plus grand est…" — is masked wherever it appears, which can garble a question and attribute it to that dossier; and a cote or road the member types as D<n> can be taken by the model for a dossier ref if it matches one it was shown (the prompt tells it not to). Mistral's default API retention is 30 days for abuse monitoring; Zero Data Retention needs a paid plan and an approved request, and the training opt-out is a separate setting.
**Before any real firm uses it (Yann):** (1) choose the provider route — Scaleway Generative APIs (existing sub-processor, no prompt storage) is the recommendation, or Mistral with ZDR and training opt-out confirmed in writing; (2) add the provider to `/privacy` and `CLAUDE.md` §5 and notify client firms, per rule 6; (3) accept or mitigate the free-text residual risk above; (4) review the EU AI Act position for AI features touching staff activity, as part of the stage 7 DPIA pack. ## D-017 · Email verification is required to sign in — DECIDED (closes B5 in code; needs a Brevo key wherever it runs)
**Date:** 2026-10-01 · **Owner:** Darwin
**Context:** B5: a plain signup was usable at once, so anyone could register someone else's address. The 2026-09-30 audit also found BUG-3: better-auth 1.7.5 deletes the password of an account whose address was never proven the first time its owner signs in by magic link — and every account was unproven. There was no password reset either, so such a user could only ever use magic links again.
**Options:** (1) Require verification: signup sends a link, sign-in waits for it. (2) Send the link but let the unverified account sign in — signup keeps working without email delivery, but unverified accounts still lose their password on a first magic link. (3) Leave it and only seed the demo accounts as verified.
**Decision:** (1), chosen by Darwin. `requireEmailVerification`, a verification email at signup and again on any sign-in attempt before verifying, and the link signs the user in. Added with it: password reset by emailed link (`/forgot-password`, `/reset-password`) and a password change in Paramètres. A magic link now only signs in to an existing account (`disableSignUp`); for an unknown address nothing is sent and the form answers the same. Emailed auth links open on `WEB_ORIGIN` and return there (BUG-4) — set on the server, not trusted from the request — so they reach the API through the app's own `/v1` rewrite and the session cookie belongs to the app's host even where the API has a host of its own. A magic-link or password-reset request answers the same, in about the same time, whether or not the address has an account; a send that fails for an existing account is logged (no address, no link) rather than reported, so on a host without email delivery the form says "sent" and nothing arrives. An accepted invitation proves the address, so it sends no second email; the seed presets the demo accounts as verified.
**Consequences:** signup needs email delivery. On the Vercel beta, `acte-api` has no `BREVO_API_KEY`, so **new signups, magic links and password resets will fail there until the key is set** (existing accounts still sign in with their password). Migration 0004 marks accounts created before this change as verified so they are not locked out — acceptable only because the beta holds synthetic data; no real firm has an account. Accepting an invitation for an address that already has an account is refused before signup is attempted (with verification on, better-auth answers a duplicate signup with a made-up success).

## D-020 · Validated time keeps its rate; an invoice draft bills time once — DECIDED
**Date:** 2026-10-01 · **Owner:** Darwin
**Context:** Two audit findings. Every revenue figure multiplied minutes by the member's *current* rate, so a rate change re-priced the past — while the edit-rate modal says a new rate applies to the next validated time. And an invoice draft billed all validated time ever on the dossier, tracked nothing as invoiced, and could be generated twice through the API for the same minutes (BUG-5).
**Decision:** `task.rate_cents` is stamped with the member's rate when the task is validated, and every figure (Home, Stats, CSV, invoices) prices a task at its own rate. `task.invoice_id` is stamped when the task's time goes onto a draft; a draft bills only validated time with no invoice yet, in one transaction, and its period label comes from the billed tasks' dates. Invoiced time can no longer be un-validated or moved to another dossier. Invoice numbers are `FA-<year>-NNN`, counted per firm and per year, with a unique index. "Ce mois-ci" figures (dossier cards, team table, source split) are now really the current Paris month; the budget bar and the budget alert still measure all validated time against the budget.
**Consequences:** migration 0004 backfills: validated tasks take their author's rate as of the migration, and time validated before an existing draft is attached to that draft. Drafts still cannot be issued, edited or deleted, and there is no PDF — that remains stage 6.

## D-021 · First-run welcome, help centre and guided tours — DECIDED (Yann to review the copy before a real firm sees it)
**Date:** 2026-10-01 · **Owner:** Darwin (asked for it) · Yann (reviews the French copy)

**Context:** The prototype has no onboarding or help UI of any kind, and no ROADMAP stage lists one (stage 7's "onboarding flow for OS permission prompts" is the Companion's). `CLAUDE.md` §1 says not to redesign and §8 says to stop when a change would alter the prototype's appearance. - **Contract and API** — `OnboardingState` (`packages/contracts/src/onboarding.ts`), `GET /v1/me/onboarding`, `POST /v1/me/onboarding/complete`. The checklist is recomputed from the member's own rows on every read; nothing is stored for it.
